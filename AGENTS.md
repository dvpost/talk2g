# talk2g

> Локальная русская диктовка: после паузы распознанный текст вводится в выбранное приложение.

## Правила работы

- Следуй [конвенции 2026.10.1](https://github.com/dvpost/coding_testing_and_docing_conventions/blob/b1cb83e9abce14f4688e5fdab7a94ca7604b85b3/coding_testing_and_docing_conventions.md)
  из `dvpost/coding_testing_and_docing_conventions`, тег `v2026.10.1`,
  commit `b1cb83e9abce14f4688e5fdab7a94ca7604b85b3`.
  Локальной копии нет; применяй закреплённую ревизию, а не меняющийся main.
  Перед изменениями M/H проследи вызывающих, потребителей, побочные эффекты
  и соответствующие тесты; для H сохрани рабочий план в `TODO/active/`.
  Все планы храни в `TODO/` в корне проекта.
- Выполняй один основной путь; при отказе показывай ошибку и прекращай
  операцию. Новые retry, fallback и защитные обёртки без явного согласования
  оператора запрещены. Предложения исключений храни только в `TODO/`;
  проверки входов, фокуса, целостности и очистку ресурсов сохраняй.
- Для действующих согласованных исключений сверяй код, маркер EXC-ID,
  одобрение и тесты с [реестром](docs/exceptional_execution_paths.md)
  в обе стороны по §12 конвенции. Неутверждённые случаи фиксируй в `TODO/`.
- CURRENT STATE ONLY: описывай подтверждённое текущее состояние; заменяй или
  удаляй устаревший текст. Завершённые планы и архивы не используй как активные
  инструкции; к Git history обращайся для целевого расследования.
- Подробные документы храни в `docs/`, README — краткий старт и ссылки.
  Версию конвенции объявляй только здесь; остальные документы ссылаются
  на AGENTS. Для каждого контракта сохраняй один источник. Результаты
  разовых проверок и статус соответствия сообщай в отчёте задачи/PR/CI.
- NO DEAD CODE: перед удалением проверь вызывающих, внешние контракты,
  регистрации Qt, CLI и сборку. Подтверждённо неиспользуемую реализацию
  удаляй вместе с её настройками, зависимостями и тестами; историю хранит Git.
- Сохраняй WebSocket v1, формат настроек и пользовательские данные.
  При несовпадении кода и требований исследуй причину до изменения поведения.
- Распознавание выполняется только целыми блоками после `recognition_pause`
  или Stop; клиент требует `ready.recognize_on_pause=true` перед передачей PCM.
  Ответы WebSocket проверяй в `protocol.py` до передачи потребителям Qt/CLI.
- Держи сервер и обработку текста независимыми от Qt; вкладки UI передают
  намерения контроллеру, который управляет записью и системными службами.
- Разделяй модули по ответственности (§4.6): сохраняй явные границы,
  не смешивай независимые обязанности и не добавляй бессодержательные слои.
- Проверяй запись и ввод на временных профилях и в отдельных тестовых окнах.
  Сохраняй работающий пользовательский экземпляр; для native X11 используй
  `benchmarks/check_x11.sh`, а не текущий рабочий стол.
- Используй синтетические токены в тестах, временные файлы в фикстурах;
  `.data`, `models`, `recordings` и отчёты запусков оставляй вне Git.
- Новые и содержательно изменённые тесты проверяют публичный результат: русские GIVEN/WHEN/THEN,
  именованные случаи, детерминированные часы; подменяй внешние границы,
  а контракт файлов/SQLite/WebSocket проверяй с реальной интеграцией.
  Ожидания задавай независимо от реализации; успех, отказ и отсутствие
  действия разделяй. Для каждого нового теста докажи RED → GREEN, мутации
  выполняй изолированно и отменяй. Старые тесты не мутируй массово ради отчёта.
- Выполняй отдельные простые shell-команды без цепочек; исследуй локальные
  файлы через `rg` и существующие утилиты.
- При изменении команд, границ или контрактов обновляй `AGENTS.md` и
  затронутые документы. В отчёте разделяй выполненные проверки,
  пропущенные проверки и оставшиеся риски.

## Команды

Из корня репозитория:

```bash
uv sync --frozen --extra desktop --extra dev
./check.sh
./check.sh tests/test_protocol.py tests/test_server.py
uv run python scripts/check_docs.py
uv run ruff check src tests benchmarks packaging scripts
uv run ruff format --check src tests benchmarks packaging scripts
./run-linux.sh app --background
```

Для Windows и проверок с дополнительными системными зависимостями,
реальной моделью или сборкой используй команды и условия из `docs/VALIDATION.md`.
