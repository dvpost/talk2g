# Потоковый протокол v1

`GET /health` возвращает JSON с `app=talk2g`, `protocol=1`,
`ready`, `busy`, `model`, `error`. WebSocket: `/v1/dictate`.
Браузерные соединения с Origin отклоняются. Клиент использует duplex-соединение:
передача звука продолжается во время получения результатов.

Первое текстовое сообщение:

```json
{"type":"start","version":1,"rate":16000,"format":"pcm16","session_id":"uuid","token":""}
```

Сервер распознаёт только целые блоки после паузы или Stop и отвечает `ready`
либо `error`. `recognition_pause` (0.5–10 с, по умолчанию 3 с) задаёт полную
тишину до отправки блока модели. Новая речь сбрасывает ожидание.
Сервер подтверждает поддержку в `ready.recognize_on_pause=true` и сообщает
`ready.recognition_pause`. Клиент требует подтверждение перед передачей PCM.
Необязательный признак `start.recognize_on_pause` допускает только true;
false или неверный тип завершают handshake с явной ошибкой.
`save_recordings` (boolean, по умолчанию серверная настройка, обычно false)
запрашивает сохранение принятого PCM и журнала в папке `recordings` сервера.
При этом `ready.recording_path` содержит путь папки сессии, либо
`ready.recording_error` сообщает об ошибке создания архива. Диктовка продолжается
по [EXC-0003](exceptional_execution_paths.md#exc-0003--продолжение-распознавания-при-файловой-ошибке-аудиоархива).
Ответ `ready` содержит имя используемой модели. Неизвестные параметры игнорируются.
Далее клиент отправляет бинарные пакеты little-endian signed PCM16, mono,
16000 Hz. Рекомендовано 100 мс, максимум 1 секунда. Максимальная сессия — 2 часа.
Буфер аудио ограничен 300 секундами накопленной речи;
при переполнении сервер завершает сессию
с понятной ошибкой вместо неограниченного потребления памяти.

События сервера:

```json
{"type":"commit","seq":1,"delta":"Привет","audio_end":0.6,"decode_seconds":0.2}
{"type":"recognizing","audio_start":0.0,"audio_end":3.0,"capturing":true}
{"type":"segment_end"}
{"type":"session_end","text":"Привет мир.","audio_seconds":3.0,"elapsed_seconds":3.2}
{"type":"recording","status":"error","message":"Ошибка записи на диск"}
```

Сессионные события включают исходный `session_id` (по умолчанию пустую строку).
Ответ `error` может приходить без `session_id`, включая ошибки до допуска
сессии. Клиент не должен требовать это поле для обработки ошибки.
Клиенты Qt и CLI проверяют JSON до передачи события потребителю: текстовое
сообщение, объект, известный тип v1 и типы значимых полей. `commit.seq` —
положительный integer (boolean не допускается), `delta` — непустая строка;
итоговый `text`, сообщения ошибок и пути записи — строки. `recognizing`
требует числовые `audio_start`/`audio_end` и boolean `capturing`.
Временные значения, если переданы, конечны и неотрицательны;
`recognition_pause` находится в диапазоне 0.5–10. Необязательные метрики,
session_id и дополнительные поля не становятся обязательными.
Неизвестный тип события или неверное поле прекращает сессию с явной ошибкой,
сохраняя уже подтверждённый текст. Локальные события клиента `loading`,
`model_ready` и статусы архива `started`/`saved` не являются wire-событиями v1.
`seq` увеличивается на единицу;
`delta` содержит только новый текст со всеми нужными пробелами. Клиент вводит
только commit. `recognizing` означает начало обработки готового блока;
далее отправляются один commit (если текст непустой) и segment_end. Событий
partial нет. Приём следующего блока продолжается во время обработки предыдущего.
Повторный seq игнорируется, пропуск останавливает клиента. Итоговый `text`
должен равняться конкатенации delta. Повторно вводить его не нужно.
При успешном сохранении `session_end`, `cancelled` и `error` содержат
`recording_path`. WAV и итоговые метаданные закрыты до отправки этого события.
Сбой сохранения после начала сессии передаётся событием `recording` и не
останавливает распознавание. Если в ready нет ни recording_path, ни recording_error,
клиент завершает подключение с ошибкой до передачи PCM.

После отправки всех аудиопакетов клиент отправляет `{"type":"stop"}`.
Сервер сохраняет последний неполный кадр, немедленно ставит текущий блок
на распознавание без ожидания паузы, обрабатывает очередь и выдаёт commit и session_end.
`{"type":"cancel"}` отбрасывает непроверенный хвост, возвращая cancelled
с уже подтверждённым текстом. Разрыв соединения освобождает сервер.
Автоматический повтор аудио после разрыва не выполняется: системная вставка
не предоставляет транзакции, и повтор мог бы напечатать текст второй раз.

Ошибки handshake и параметров передаются как `{"type":"error","message":"…"}`.
Входной start ожидается не более 10 секунд. Отказ в авторизации, занятость,
неверный PCM или управляющее сообщение не оставляют сервер занятым.
При ошибке распознавания уже переданные commits остаются результатом клиента;
вместе с ошибкой архив, если доступен, содержит принятый звук и серверный текст.
При несовпадении session_end.text с полученными commits клиент показывает
ошибку и сохраняет подтверждённый текст без замены серверным итогом.

Контракт реализуют [protocol.py](../src/talk2g/protocol.py),
[server.py](../src/talk2g/server.py) и [session_output.py](../src/talk2g/session_output.py).
Исполняемые проверки — [test_protocol.py](../tests/test_protocol.py),
[test_server.py](../tests/test_server.py) и [test_session_output.py](../tests/test_session_output.py).

Результат каждого независимого вызова добавляется целиком, сохраняя
произнесённые повторы и уже введённые пользовательские символы.
