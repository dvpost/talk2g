# Сервер, настройки и диагностика

Команды ниже выполняются из корня репозитория исходников. На Windows
используйте `run-windows.cmd` вместо `./run-linux.sh`.

## Модель и дополнительные настройки

По умолчанию используется **GigaAM v3 E2E CTC INT8 на CPU**, четыре потока.
Механизм сегментации и подтверждения текста описан в
[архитектуре](ARCHITECTURE.md#подтверждение-текста).


Уже введённый текст не переписывается; ошибки модели можно исправить после остановки.

Задержка зависит от оборудования и настроек, качество — от голоса, шума
и микрофона. Скрипты в [benchmarks](../benchmarks) измеряют работу приложения
на выбранной записи.

В настройках можно изменить микрофон, хоткей, адрес сервера и паузу распознавания
и тайм-аут без речи (`idle_timeout`, по умолчанию 45 секунд).
Дополнительные параметры находятся в `.data/settings.json`: `threads`, `model`.
Неизвестные поля профиля игнорируются и не записываются при сохранении.
Для альтернативной RNNT-модели:

```bash
./run-linux.sh download --model gigaam-v3-e2e-rnnt
./run-linux.sh server --model gigaam-v3-e2e-rnnt
```

Чтобы приложение автоматически запускало RNNT, завершите его, установите
`"model": "gigaam-v3-e2e-rnnt"` в настройках и запустите снова. При существующем
сервере фактическая модель определяется этим сервером.

## Фоновый или удалённый сервер

Сервер стартует автоматически с интерфейсом или по хоткею, в зависимости от
галочки загрузки модели. Отдельный запуск полезен, если нужно держать модель
загруженной независимо от окна:

```bash
./run-linux.sh server
./run-linux.sh doctor
./run-linux.sh transcribe tests/fixtures/example.wav
./run-linux.sh replay tests/fixtures/example.wav --events benchmarks/replay-events.json
```

Для Windows заменяйте `./run-linux.sh` на `run-windows.cmd`.
`doctor` показывает аудиоустройства и зависимости. `/health` сообщает готовность.
Интерфейс подключается к `ws://127.0.0.1:8769/v1/dictate` и может использовать
уже работающий экземпляр сервера. Одновременно разрешена одна диктовка.
Галочка управляет жизнью только локального сервера, запущенного самим приложением;
уже работающий отдельный или удалённый сервер клиент не выгружает.

Для сетевого сервера задайте `TALK2G_TOKEN` перед запуском с
`--host 0.0.0.0`, укажите такой же токен в интерфейсе клиента. В недоверенной сети
используйте `wss://` через TLS-прокси. Протокол описан в [PROTOCOL.md](PROTOCOL.md).

## Каталоги и профиль

По умолчанию профиль находится в папке проекта или автономного приложения.
`TALK2G_HOME` переопределяет каталог профиля; интерфейс также принимает
`app --home`. Настройки, история и журналы находятся в `.data` этого каталога.

| Каталог | Назначение |
| --- | --- |
| `.data` | Настройки, SQLite-история и журналы приложения/сервера |
| `models` | Локальные веса GigaAM и Silero VAD |
| `recordings` | Сохранённое сервером аудио при включённом архиве |
| `.venv`, `.venv-win` | Python-окружения исходного проекта для Linux и Windows |
| `.tools` | Дополнительные системные библиотеки Qt и инструменты, устанавливаемые локально |
| `build`, `dist`, `*.spec` | Артефакты сборки; могут быть удалены, если готовая поставка больше не нужна |

Профили, окружения, веса, записи и артефакты не входят в Git. При включённом
копировании после завершения clipboard содержит всю диктовку.
При удалённом сервере `recordings` находится на сервере.

## Журналы и диагностика остановки

| Журнал | Когда создаётся и что содержит | Хранение |
| --- | --- | --- |
| `.data/app.log` | При запуске интерфейса: готовность приложения с PID, хоткей, состояние диктовки и ошибки приложения | Ротация при 1 000 000 байт, две резервные копии `app.log.1` и `app.log.2`; права файла 0600 |
| `.data/server.log` | Когда интерфейс запускает собственный сервер: stdout/stderr процесса модели, готовность и ошибки сервера | Вывод дописывается; автоматической ротации нет |
| `.data/launcher.log` | При ручном перенаправлении вывода: stdout/stderr запускающего скрипта, Python и Qt, включая сообщения до открытия `app.log` | Управляется командой запуска; автоматической ротации нет |

`app.log` и `server.log` находятся в выбранном профиле `TALK2G_HOME`
или `app --home`. Отдельная команда `./run-linux.sh server` выводит сообщения
в терминал; `server.log` открывает именно интерфейс для своего дочернего процесса.

Для ручного запуска Linux в отдельной сессии процесса с сохранением вывода,
из корня проекта в графическом сеансе выполните отдельные команды:

```bash
mkdir -p .data
touch .data/launcher.log
chmod 600 .data/launcher.log
setsid -f ./run-linux.sh app --background >> .data/launcher.log 2>&1 < /dev/null
```

`--background` выбирает запуск в трее; `setsid -f` отделяет процесс от терминала.
Файл `launcher.log` создаётся оболочкой при перенаправлении вывода; обычный
запуск и запись автозапуска сами этот файл не создают. `>>` дописывает вывод,
сохраняя сообщения прошлых запусков; `>` перезаписывает файл. В этих командах
путь `.data/launcher.log` относится к каталогу проекта и не меняется при
задании другого `TALK2G_HOME`; при другом профиле укажите нужный путь явно.

Для проверки работающих процессов и последних сообщений в профиле проекта:

```bash
pgrep -af '[t]alk2g'
tail -n 80 .data/app.log
tail -n 80 .data/server.log
tail -n 80 .data/launcher.log
```

При включённой загрузке по требованию собственный сервер завершается после
диктовки, а интерфейс остаётся работать. Сообщение об остановке диктовки
означает завершение записи. Штатный выход из приложения сейчас не имеет
отдельной записи в журнале; завершение сигналом или авария также могут
не оставить сообщения. Последняя строка журнала и отсутствие ошибок сами
по себе не устанавливают время и причину остановки процесса. Для расследования
нужны также системный журнал и дамп падения, если они доступны.
